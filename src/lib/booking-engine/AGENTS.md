## Booking engine rules
- Guests, Stripe and cron reach bookings only through the db/0216 `rout_booking_*` SECURITY DEFINER entry points; never widen rout_app RLS or query booking tables without a session. Why: anonymous code must not see any host's rows, and every check lives where the write happens.
- `rout_booking_create` is the only way to insert a booking: it derives status/hold from the event type, validates grid/notice/horizon/cached availability over the whole block, and locks every (host, UTC day) the block touches in global order. Why: no caller can book outside working hours, and cross-midnight or shared-seat races serialize.
- Per-user background work (recompute, calendar sync, guest mails) runs inside `withDbContext({ userId: host })`. Why: cron acts as the owner through RLS instead of around it.
- Team slots are computed per host and only then combined (`slot-rules.ts`); collective = every host, otherwise any single host. Why: partial free time of different hosts is never stitched into one slot.
- Collective bookings change as one group (paid, release, confirm, decline, cancel). Why: one guest booking must never end half-confirmed.
- Wall time → UTC follows RFC 5545 (gap moves forward, ambiguous takes the first); external recurrences expand on the event's own wall clock via `rrule`. Why: weekly meetings must not drift an hour across DST.
- External calendar URLs pass `assertCalendarUrl` (https/443, no userinfo, public DNS via the shared SSRF guard, no redirects) both before they are stored and before every sync. Why: a member must never make the server reach an internal address.
- Soft-locks (db/0218 `booking_holds`, 5 min, secret stored as sha256, max 3 live per client digest) are taken and consumed only by `rout_booking_hold` / 9-arg `rout_booking_create` under the same (host, day) locks; holds count for overlap, seats and limits of everyone else. Why: a guest typing their details must not lose the slot, and no visitor can pin the calendar.
- Day/week/month limits, per-guest caps, the business-day horizon and adjacent-only starts are decided in SQL (`rout_booking_pick_hosts`, `rout_booking_start_problem`); the slot list mirrors them via `rout_booking_public_constraints` and `horizonEndUtc`. Why: one authority, the UI can only hide slots, never allow them.
- App code detects phase-2 schema at runtime (`phase` in the public type, `to_regclass('booking_holds')` for saves) instead of assuming it. Why: code may deploy before a reviewed migration is applied on Neon.
- Group sessions (shared seats) reach the slot list via db/0219 `rout_booking_public_sessions`: overlapping starts are hidden, the session's own start only while bookings + others' holds leave a seat. Why: the list must offer exactly what `rout_booking_host_free_held` accepts.
- `calendar_events` is owner-scoped through `connected_calendars` (db/0220); only the definer booking checks read other hosts' busy times. Why: one member's calendar must never be readable in another member's session.
- Adding or manually refreshing an outside calendar first passes `allowCalendarFetch` (per-member shared counter, RATE_RULES.calendarFetch, fail-closed). Why: a member chooses the address the server fetches, so the number of fetches must be capped too.

## Phases B–G (owner's hard requirements)
- Booking E2EE: keys recoverable only via recovery-mpc shards; blobs/RVE1 always hybrid ML-KEM-1024+X25519; booking and bitmap traffic padded to fixed sizes with constant response time; Omni worker never holds vault/device keys or plaintext. Why: privacy-preserving recovery, harvest-now-decrypt-later, side channels, blind worker.
- Hardware binding: device keys are generated non-extractable in the crypto worker and their seed is unwrapped only with a WebAuthn PRF secret from a passkey whose attestation proved a hardware authenticator (TPM 2.0 / Secure Enclave / security key) at registration; a device without such a passkey gets no booking keys. Device change restores only through recovery shards. Why: browsers cannot run arbitrary E2EE ciphers inside the TPM, so the hardware-held PRF seed is the strongest binding the web platform offers, and docs must say so.
- Zeroization: every owned key/plaintext byte buffer lives in a pre-allocated buffer from one worker-side arena and is zero-filled in finally, with a test asserting the arena is all zeros after each operation. Why: JS cannot erase GC or engine copies, so ownership must be explicit and the residue measurable.
- Property-based and model-checked proofs: ledger, hash chains, holds/locks and booking state transitions each get fast-check properties plus an exhaustive bounded model check of interleaved operations against the SQL rules; a Phase B migration without them is not ready for GO. Why: race freedom and no state bifurcation must be shown over generated schedules, not single examples.
- Guest anonymity: a guest's right to a slot is a BBS+ (BLS12-381) credential issued blind; at arrival the guest shows a zero-knowledge proof. The server keeps only a slot-scoped nullifier and a host-scoped pseudonym (per-guest caps work per host, never across hosts); guest contact for mails exists only as a vault ref. Why: an encrypted booking must not link back to the guest, and no one can follow a guest from host to host.
