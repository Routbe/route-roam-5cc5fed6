## OAuth provider rules
- Consent and step-up RPCs require the member session, never developer workspace access; console management RPCs keep requireDeveloperAccess. Why: being a workspace editor must not prevent login VIA ROUT or weaken app-management permissions.
- Integration examples share button-kit.ts; authorization is user-initiated and unavailable APIs must remain disabled. Why: generated instructions must not activate unimplemented login or issuance paths.
- Account-discovery prompts prohibit silent login and email-only merging; linking requires an existing local session, consent and conflict checks. Why: discovering matching data is not authorization to take over an account.
- OAuth client console settings (publishing status, PKCE, token TTL, IP allowlist, account discovery) are enforced in `provider.server.ts`/`console.functions.ts` (this folder) server-side, never only in the UI. Why: the console is the developer's control plane; the OIDC endpoints are the security boundary.
- New OAuth client secrets are stored as `v2$` peppered SHA-256 (`client-secret.ts`), legacy plain hashes stay valid until rotated. Why: no forced re-issue for existing apps.
- `rout_handle` is shared only when the app enabled Universal Handle Sync (`handle_sync_enabled`, db/67) and `profile` was granted (`routHandleClaim`). Why: apps must opt into identity data.
- Redirect URIs use byte-for-byte registered-value matching in redirect-match.ts; no decoding, trimming, case folding, slash or port normalization, wildcards, credentials or encoded separators. Why: callback capability binding must reject every non-exact URI.
- client_credentials tokens follow pure `m2m-rules.ts` (exactly 900 s, never identity scopes, confidential clients only). Why: a machine token must never act as a person.
- Private relay addresses (`priv-<hex>@mail.rout.be`) come only from `email-forwarding.ts` (pure rules) + `email-forwarding.server.ts`; inbound mail enters only via `/api/public/email-forward` (token auth) and `oauth_email_deliveries` stores transport metadata only (db/0137). Why: no sender, subject or content of a member's mail is ever kept.
- Per-app primary email assignments are consent snapshots; unavailable private choices omit email, never fall back to primary. Why: a changed address or failed lookup must not bypass consent.
- Sensitive UserInfo responses require a successful disclosure-log write; webhook registration and delivery use `assertPublicHost` and refuse redirects. Why: disclosure must be auditable and private-address hosts rejected; egress controls are still needed against DNS rebinding.
- Every `sub` sent to an app (id/access tokens, refresh, introspection, userinfo, events) comes from `subject-vault.server.ts`: HKDF(ROUT_SUBJECT_MASTER_KEY, length-encoded version|sector) → HMAC over the account id, recorded in `oidc_subjects` (db/0196–0197). Stored legacy subjects are never re-emitted; `previous_sub` comes only from older vault versions. Why: the account id must never reach a JWT and a leak at one app must not link to others.
- The `picture` claim is a per-app sealed proxy URL (`picture-proxy.server.ts`, `/api/public/oauth/picture`) that only serves while the consent is active. Why: avatar paths start with the account id and identical URLs would let apps link members.
- Console app lists are per context: personal = caller's own apps, workspace = all apps of that workspace (RLS rout_scope limits to members). Why: workspace apps must not vanish for teammates.
- `linked_accounts` is accepted but never emitted. Account recognition is Blind Hash Matching (`blind-hash.ts`): partner SHA-256 hashes (client_id domain-separated, URL fragment only, never stored/logged) are compared in the enclave worker; the one identity the member confirms is re-verified server-side and sealed inside the authorization code (`code-disclosure.server.ts`), emitted only as id_token `rout_matched_account`. Why: owner veto — apps must never see a member's other accounts.
- `/oauth/end-session` ends a session only for same-origin/typed requests (`isTrustedLogoutRequest`); cross-site GET/POST gets a confirmation page that POSTs back. Why: the Lax session cookie rides cross-site GETs, so any site could otherwise sign members out.
- Workspace apps are managed by owner/admin/developer members of the caller's active workspace and personal apps only by their creator (`client-access.ts`, every owner-scoped function in `provider.server.ts`); the irreversible pairwise switch needs owner/admin. Why: teammates must edit apps and rotate secrets without the creator, and leaving a workspace ends access.
- `rout_handle_reservation` (scope `identity:handle_reservation`) comes only from `handle-reservation.server.ts`: root handle of an active, e-mail-confirmed, unbanned account, unique in ROUT, rate-limited per member+app, failing closed to `unavailable`. Why: apps adopt the name without their own anti-bot checks, so ROUT must never vouch for an unchecked name.
- Member e-mail pushes (`pushAppEmail`) await webhook delivery and report per-app outcomes via `email-push.ts`; an app counts as notified only after a 2xx. Why: the member must see which apps really know the new address.
- The native "ROUT ID" sign-in takes its endpoints from native-endpoints.ts (shared with the discovery document) and reads identity only from userinfo with the access token, keyed by `sub`. Why: a self-fetch of discovery per auth request failed on cold or protected hosts and silently skipped the provider.
