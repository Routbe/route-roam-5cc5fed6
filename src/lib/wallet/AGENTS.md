## Wallet rules
- Profile Google claims use owner-authenticated createWalletPass; both legacy Google profile endpoints independently enforce the same server-resolved owner/namespace match. Profile cards (Google, Apple, 3D viewer) share generateWalletPayload → walletCardPayload; incomplete credentials disable issuance. Why: callers cannot claim another member's pass or bypass ownership through legacy endpoints.
- The 3D ROUT Card (`components/wallet/RoutCard3D.tsx`) is lazy-loaded inside a dialog and falls back to the CSS card drawn from the same canvas faces when WebGL is missing or crashes. Why: three.js never enters SSR or the first page load.
- Card numbers (sovereign IDs) are HMAC(WALLET_ID_SECRET) over space + account id, falling back to a hash of public handle data only. Why: a card must never reveal or be derivable from the internal account id, and root/alias cards must stay unlinkable.
- Pass serials derive one-way from the card digest, never from the handle; public wallet endpoints accept handles only, account ids only via server code passing `allowAccountId`. Why: renaming a handle must not orphan saved passes, and account ids must not be probeable.
- Dual-layer scans: the printed metal-card QR is `/v/<sealed id>` (card-public-id.ts) and only shows public identity + kill-switch state, never authenticating; authorisation is the NFC handshake at `/api/hardware/verify` or the owner-only rotating digital token at `/s/<token>` (forwarded to `/kaart/<token>`, verified on open, single-use). Why: a lost or photographed metal card must grant nothing.
- Card freeze lives in `card_freezes` (db/0198, owner-applied) and is read only via security-definer `rout_card_frozen`; a frozen serial gets no live code or secure QR and fails every verify path. Why: a lost card must be killable instantly without exposing who owns it.
- Google-only premium art and payload use google-premium-art: one shared official ROUT badge as logo, an OKLab jewel-tone tile mixed from profile canvas + accent (wallet-color.ts, white text ≥ 4.5:1), and a text-free, photo-free hero per card served from versioned public-handle PNG routes; legacy artwork and Apple/3D colours remain unchanged. Why: upgrade Google Wallet without changing other surfaces or exposing account IDs.
- Owner-verified Google save flows first push the current class + object through the Wallet REST API (google-wallet-sync.server.ts, best-effort, time-boxed); public pass routes never do. Why: Google ignores the JWT object for passes already saved, so redesigns would otherwise never reach existing cards.
- Google Wallet console PNGs in public/assets/wallet are regenerated from wallet-art.ts (resvg + Inter), never hand-edited, because artwork must stay identical to the per-member hero renderer.
- The query-style hero URL redirects public handles to the canonical renderer; it must never introduce account-ID lookup or bypass publication checks. Why: console compatibility preserves the existing privacy boundary.
- Google ROUT Cards and event passes are Loyalty passes (loyaltyClass/loyaltyObject). Tile colour and logo exist only on the class, so each harmonised tile colour gets its own class `<GOOGLE_WALLET_CLASS_ID or issuer.rout_card>_<hex>`; the object carries the @handle as accountName (primary card row) and keeps long security texts in textModulesData only. Why: Google rejects colour/logo on loyalty objects, and members must keep their own colour.
- Every generated Wallet image response uses WALLET_IMAGE_HEADERS (open CORS, one-year immutable). Why: image URLs are versioned by design, so the bytes behind a URL never change.
- Wallet export is three separate passes (wallet-key.ts): PUBLIC_PROFILE (root, QR, no NFC), STEALTH (alias, QR, no NFC) and SMART_TAP_KEY (no QR, no handle/name/URL; NFC token only via Google Smart Tap or Apple VAS). Key serials/tokens are HMAC(WALLET_ID_SECRET) with their own labels and the key stays disabled until Smart Tap / Apple NFC approval is configured. Why: a shown or scanned profile card must never carry or reveal the NFC key.
- apdu.ts is the ISO 7816-4 protocol core for a native HCE service or reader; browsers cannot emulate cards (Web NFC is NDEF only), so nothing in the web app claims card emulation. Why: keep the protocol tested without promising impossible browser behaviour.
- The 3D/CSS card front QR is rout.be/<handle>/<6 digits> from card-front-code.ts (HMAC of the card key over serial + 10-minute window), given only to the owner of an active root card; `$username_/$slug` redirects unmatched 6-digit (and legacy 4-digit) codes to the public profile and `/api/public/card-check` answers only `{fresh}`, limited per IP and per card. Why: the front is public and may be photographed; freshness is the only signal partners get.
- RoutCardDialog reveals the stage only when the scene is ready and the first liveness/secure-token answers are in (8 s safety reveal). Why: the card must never show undecorated and then pop its effects in.
- Owner decision (Nov 2026) narrowing the key-pass rules above: the Google Sovereign Key also carries a Google-rotated TOTP QR (`rout:wk:<key id>:<8 digits>`, 60 s, secret = HMAC(WALLET_ID_SECRET) over the key id), verified single-use per step at `/api/access/verify`; the Apple key stays NFC-only because Apple cannot rotate a barcode. Why: a fixed payment QR could be photographed and replayed.
- The owner picks the ROUT card front QR target (root profile digits URL or `/u/<alias>`), stored in `profiles.display_prefs.cardFrontTarget`; the back QR is always the secure access token. Why: the front is a profile-card link, the back is for payments only.
- Every owner wallet issue path (vault, key pass, alias claims) requires `isVerifiedMember` (a resolvable verified root profile). Why: only verified members get the three wallet cards.
- Freezing, thawing, blocking and replacing the ROUT card all require 2FA plus a single-use card_lifecycle step-up, then best-effort switch the saved Google key pass ACTIVE/INACTIVE (setGoogleKeyPassState). Why: the database decides; the phone should agree without the save link ever depending on Google.
- NXP NTAG 424 DNA taps arrive on `/t?p=<PICCData>&m=<CMAC>`, and `history.replaceState` strips the query before any server call; tap URLs carry no card id or user reference (unlinkable by design). The server decrypts PICCData with the fleet key and checks the CMAC with the AN10922-diversified card key, and `vault_enclave` (begin/confirm/consume_sdm_tap, db/0245) enforces lockout, a strictly rising counter and single-use grants. First-tap activation (db/0246) spends that grant through `activate_member_card` for the signed-in caller only. Why: a copied, replayed or photographed tap URL must never prove or claim a card.

- Vault tap consumption and card activation run as SERIALIZABLE batches via runSerializable (src/lib/neon.ts), retried with jittered backoff only on 40001/40P01; secret byte comparisons in SQL use vault_enclave.ct_equal_32, and every vault_enclave table carries a restrictive deny_all RLS policy (db/0247). Why: a rolled-back serializable batch is safe to re-run, and an accidental grant must still return no rows.
- Card batch keys leave ROUT only as an HPKE (RFC 9180, DHKEM P-256, AES-256-GCM) bundle sealed server-side to a station pinned in vault_enclave.sdm_stations (db/0248); the info string binds batch id and station fingerprint, and mark_sdm_batch_exported(batch, station) logs the export and hands out the sealed envelopes in one transaction. Why: no plaintext key in transit, and no key without an audit row.
- A physical card tap is a step-up method ("card"): the dialog opens a single-use db/0250 intent (HttpOnly cookie), a verified owner tap completes it (in-dialog Web NFC, or on /t only after the member presses confirm there), and claiming it issues the signed proof for the scope stored with the intent; blocking or replacing the ROUT card revokes the member's physical cards (db/0253). Why: the browser never chooses the scope, an unrelated tap can never approve a request started elsewhere, and a lost chip must stop confirming at once.
